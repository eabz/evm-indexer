## BLOCKER

**1. Solana: `checkpoints` is the only resume/gap oracle, but it is written AFTER the commit marker → a re-stream doubles every aggregate.**
`/Users/eabz/Documents/GitHub/evm-indexer/src/pipeline/solana_writer.rs:511` inserts `sol_slots`, then `:528` inserts `checkpoints` as a **separate awaited insert**. `/Users/eabz/Documents/GitHub/evm-indexer/src/pipeline/solana.rs:1059-1090` (`resume_point`, `missing_ranges`) read **only** `checkpoint_tiling`, never `sol_slots`. `heal_gaps` (`solana.rs:1180-1190`) purges a hole only when `has_orphan_children` is true, and that predicate (`solana_store.rs:627-630`) means *children at a slot with no live `sol_slots` row*.
Failure: the marker lands, the checkpoint insert exhausts its 6 retries (`db/mod.rs INSERT_ATTEMPTS`) or `SvmWriter::abort` cancels the task between the two awaits. Those slots are now a permanent hole whose children have a **live** marker → heal skips → the range is re-streamed → fresh `_version` → different `insert_deduplication_token` (`db/mod.rs:429-436`) → every insert accepted → the MVs of `sol_dex_candles_1m/1h/1d` (`0042:68,118,168`) and the six `launchpad_*_1d` aggregates (`0031:55,104,149,182,207,238`) fire a second time into `SimpleAggregateFunction(sum,…)` columns. Base tables still read right with `FINAL`; every candle, volume and swap count in that window is doubled, permanently, with no auto-repair. The EVM path is immune because its gap query reads `blocks`, and design §2 explicitly says checkpoints are *not* the resume cursor.
Fix: in `heal_gaps`, also purge a hole that contains live `sol_slots` rows (`solana_store.rs:493-505`); a purge is idempotent, so the re-stream then rebuilds the candles correctly.

**2. Solana: no checkpoint compaction + a hard `LIMIT` on the tiling → after ~4-5 days at the head the indexer re-streams (and doubles) everything.**
`solana_store.rs:433-457` `checkpoint_tiling` is `ORDER BY from_block ASC LIMIT {limit}` with `limit = MAX_CHECKPOINTS = 100_000` (`solana.rs:133`); the **startup cursor is `resume_point()`** (`solana.rs:958-966`). `grep` for `compact_checkpoints` in `src/pipeline/solana*.rs`: **0 hits** — the EVM loop compacts after every covered pass (`mod.rs:748`), the Solana loop never does. At `TIP_CADENCE` 4 s that is 15-20 checkpoint rows/min ≈ 25k/day, so 100k live rows in ~4-5 days. From then on the tiling truncates, `contiguous_until` returns a slot far below the real head, `holes()` (`solana.rs:1470-1472`) reports everything above as a hole, and it is re-streamed over live data — finding 1's doubling applied to days of candles. EVM's `resume_point` pages the whole table with no limit (`verify.rs:577-598`).
Fix: call `Database::compact_checkpoints()` on the `PassOutcome::Covered` arm (`solana.rs:1003-1009`) behind the same fence/interval as EVM, **and** page the tiling instead of `LIMIT`.

## MAJOR

**3. `purge_stale_flushes` drains the queue destructively — a transient error loses the spans for ever (worse than the documented OPEN item).**
`src/pipeline/mod.rs:1066-1082`: `let stale = std::mem::take(&mut *self.stale.lock().unwrap());` then `for range in stale { …purge_range(…).await?; }`. On `?` the function returns `Err` and the local `Vec` — the failed range **and every range after it** — is dropped. design.md's OPEN item says only a *crash* loses them; a transient ClickHouse hiccup, a lease failure or `TombstonesNotConverging` does too, and `pass()` is then simply retried as if nothing happened. The rows are stored, so no gap query ever asks again; only `indexer verify` finds it. Same shape on Solana (`solana.rs:1373-1395`).
Fix: iterate a clone and remove only the entries that succeeded (or push the survivors back before returning `Err`).

**4. Solana bucket repair does not exclude the purged slot range — it relies on seeing the tombstones.**
`src/pipeline/solana_store.rs:934-970` `rebuild_derived` passes `purged_from = u64::MAX, purged_to = None`. design.md "Changes from hardening round 2" is explicit: *"Every module's rebuild SQL excludes the purged block range itself … a rebuild never depends on seeing tombstones"*, and `DerivedTable::rebuild_slice`'s doc gives the reason (no read-your-writes on 25.12). If one tombstone part is not yet visible to the rebuild query, the purged `sol_dex_swaps` / `launchpad_trades` are re-filed under the **new** epoch and the re-stream adds them again — a double count `epoch_floor_v` cannot hide. The `tombstone_until_gone` verification loop makes this unlikely in practice, but it is the only protection and it is the one design.md says not to lean on.
Fix: thread `{purge_from}`/`{purge_to}` through `SOL_DERIVED` and the shared launchpad rebuilds as the EVM path does.

**5. The "debris of a finished purge" rule lets a MODULE purge settle orphans it never repaired → permanent double count.**
`src/pipeline/store.rs:470-474` builds `done` = **all** `reorgs` rows with `completed = 1`, including the ones `indexer backfill --module X` writes (`backfill.rs:268-285`, `Scope::Module`, reason `redecode`, `fork_block`/`to_block` = the module hull). A module purge's `timestamp_span` (`store.rs:535-590` with `Scope::Module`) reads **only the module's tables**, so its repair window can be far narrower in *time* than its block range.
History: a flush of blocks 1000-2000 (days D1+D2) dies before `blocks`; a gap heal tombstones the core children and dies before writing its `reorgs` row; an operator runs `indexer backfill --module dex` over [1000,2000) whose dex rows fall only on D2 → completed row (1000, 2000, V_b > V_a), window [D2,D3). Next start: `has_orphan_children` sees every core orphan as settled (`settled(column)` = V_b) and skips the heal; D1 keeps the tombstoned transactions in `daily_transaction_stats` **and** counts them again when the range is re-streamed.
Fix: `AND reason != 'redecode'` in the `done` subquery — a module purge settles nothing outside its own tables.

**6. One row with `timestamp = 0` inside a purge range blanks a chain's entire aggregate history.**
Nothing clamps `from_ts`: `purge.rs:370-383` takes `min(timestamp)` over all row versions, `start_of_day(0) = 0`, so `reorgs.from_ts = 0` and `to_ts = today+1`. Measured with `clickhouse local`: `epoch_floor_v` then expands `arrayJoin(range(0, now, 86400))` = **20,715 day rows** and raises the floor for every day since 1970 — every older-epoch contribution of the chain is hidden at once — while `DerivedTable::rebuild_statements` slices [0, now) into **~678 monthly INSERTs per aggregate** (~20 aggregates ≈ 13.5k full-month scans). Until that finishes the whole chain reads as zero; if it fails it is retried from scratch. Reachable: `src/source/solana.rs:713` `block_time.unwrap_or_default()` turns a missing `blockTime` into timestamp 0, and an EVM genesis block often has timestamp 0.
Fix: refuse or clamp a `from_ts` below the chain's first known block timestamp and fail loudly instead of arming the rule.

**7. Solana: the purge's visibility gate proves the wrong table.**
`solana.rs:633-666` `wait_until_visible` polls only `sol_slots`, and `solana_writer.rs:396-401` updates `last_flush` only when the batch had slot rows (a window of only skipped slots leaves a stale `last_flush`; `solana_writer.rs:586-595` blesses that case). `checkpoints` is a separate insert. `tombstone_until_gone` stops on the **first** attempt whose live count is 0, so one stale read of `checkpoints FINAL` ends the loop with the newest checkpoint still alive. `purge_stale_flushes` then purges slots whose checkpoint survived: `missing_ranges` sees no hole, the slots are never re-streamed, and `indexer verify` reports the tiling complete. Silently missing data.
Fix: poll `checkpoints` too, and take `last_flush` from `batch.covered()`.

**8. Solana: a truncated gap listing advances the cursor past holes that are never revisited.**
`solana.rs:1130-1161`: `pass()` returns `Covered(range.to)` even when `holes()` truncated at `MAX_GAPS_PER_PASS = 1000` (`solana.rs:1463-1465`), and `heal_gaps` sets `healed_until = range.to` unconditionally (`:1212`). The un-streamed holes fall below both and are never examined again for the life of the process, while `/readyz` reports ready. Only a restart recovers. (The EVM path avoids this with `missing.covered_until`.)

**9. Solana: the parent-hash tripwire silently switches itself off at ~3% of pass boundaries.**
`solana.rs:1239` takes its predecessor from `anchor_for(range.from)` (`:1342-1364`), which returns `None` — with no log line — unless a live checkpoint ends exactly at `from`; `stream_range` then skips `check_continuity` for the first served block (`:1279`). Every head pass (~4 s) depends on a `checkpoints FINAL` read of the row the previous pass just wrote, so with the project's own measured ~3% no-read-your-writes rate roughly one boundary in 33 has the only Solana fork check disabled. The in-memory `Continuity` from the previous pass is thrown away even though it is exactly the right value.
Fix: keep the last `Continuity` in `SolanaIndexer` and use it when adjacent; `warn!` when an expected anchor is missing.

**10. Solana: a missing `block_height` / `parent_blockhash` becomes `0` and trips the fatal tripwire.**
`src/source/solana.rs:707-712` maps `None → unwrap_or_default()`. `check_continuity` (`solana.rs:418-440`) then reports a height break of ~the whole chain height or a parent-hash break; `is_fatal` (`:1484-1493`) makes it non-retryable, the writer is aborted and the operator message tells them not to restart. A transient field omission wedges the indexer and, under a restart policy, becomes a crash loop.
Fix: distinguish absent from zero in `to_batch` — a plain retryable source error naming the slot and field; reserve the tripwire for values that are present and disagree.

**11. `sol_launchpad_token_holders_v` returns wrong holder numbers.**
`migrations/0043_solana_launchpads.sql:186-206`. (a) `GROUP BY owner, balance` instead of `GROUP BY owner` with `sum(balance)`: an owner holding the mint in two SPL token accounts yields **two** rows (inflated holder count, each position understated) — and if the two accounts hold the *same* amount they collapse into **one** row and half the holding disappears. The EVM twin it claims to mirror does `sum(delta) … GROUP BY account` (`0032_launchpad_views.sql:584-598`). (b) `block_number <= {as_of_block}` is applied **after** `FINAL`, and `FINAL` keeps only the latest observation per account, so a historical `as_of_block` *drops* every account whose latest observation is newer instead of giving its balance then.

**12. `sol_token_balances` cannot be corrected by a purge.**
Schema `0043:153-171`, `_version` = packed `(slot, tx_index)` (`src/svm/launchpads.rs:369-371`), excluded from `child_tables()` and `versioned_tables()` (`solana_store.rs:44-106, 223-252`). Replays and out-of-order batches are **correct** (see Verified OK). But the code's own note — *"Nothing is lost: the range is always re-streamed"* — only holds for a gap heal. When the purged range is not re-streamed with identical content (the purge tripped the tripwire and the operator re-indexes differently or with `--no-launchpads`, or the reason for the purge is that the source data itself was wrong — the case `solana_verify.rs:21-24` calls out), the wrong balance stays live at its position `_version` and **no statement in the codebase can remove it**.
Fix: tombstone in position space — `_version = (B << 32) | 0xFFFF_FFFF` for a purge of `[A,B)` — which outranks every position inside the range and is outranked by every later observation; then the table can join `child_tables()` safely.

**13. The Solana candles lost the dust guard the EVM candles have.**
`migrations/0042_solana_aggregates.sql:70,120,170`: `trade_ok = (amount0>0)!=(amount1>0) AND amount0!=0 AND amount1!=0`. The EVM twin (`0011_dex_aggregates.sql:75,125,175`) additionally requires `abs(toFloat64(amount0)) >= 1000 AND abs(toFloat64(amount1)) >= 1000`. Since `trade_price = abs(amount1)/abs(amount0)`, a single 1-raw-unit swap produces an arbitrary price that `argMinStateIf`/`argMaxStateIf`/`max`/`min` take straight into open/high/low/close. Dust swaps are trivial and common on Solana. `launchpad_candles_1m/1h_mv` (`0031:55-80`) have the same omission for **both** families (`priced = token_amount != 0 AND quote_amount != 0`).
Fix: add the `>= 1000` conjunct to all three Solana `trade_ok` expressions and to the launchpad `priced` expression; define the threshold in one place so the families cannot drift again.

## Verified OK

- **`epoch_floor_v` overlap semantics.** Built the table + view in `clickhouse local` 25.12.1.322. Purge A (epoch 1, Jan 1-11) then purge B (epoch 2, Jan 3-5, i.e. newer but *narrower*) produces exactly `Jan1-2→1, Jan3-4→2, Jan5-10→1, Jan11→0`. The per-day `max(epoch)` formulation is correct where a running maximum would not be.
- **Sub-day buckets at both window edges.** Hourly rows on a chain with that reorg history: Dec 31 keeps its epoch-0 contributions, Jan 1-10 hide epoch 0 and count epoch 2, Jan 11+ count both. Day-granular floors are exact for 1m/1h buckets because `from_ts`/`to_ts` are always UTC day starts.
- **ASOF orientation and `join_use_nulls`.** `a.bucket >= f.from_ts` (0004) and `f.from_ts <= a.bucket` (0011/0022/0032) give byte-identical results; a chain with no `reorgs` row reads `epoch_floor` NULL → `ifNull(…,0)` → all rows count, also under `SET join_use_nulls = 1`.
- **`epoch_floor_v` cost at scale.** 50 chains × 730 days × 20 reorgs/day × 2 rows = **1.46M `reorgs` rows** collapse to 36,550 view rows (the `GROUP BY chain, d` is what bounds it — cost is chains × distinct repaired days, not reorg count): 0.032 s alone, 0.102 s for the full ASOF join over a 2M-row aggregate (plain scan 0.075 s), 0.022 s with a chain filter (which does push down). No scalability problem.
- **`u32` edges.** `day + 86400` widens to `UInt64` (no wrap) and `toDateTime` clamps at `u32::MAX`; the terminator row is emitted exactly once per contiguous run and never collides with a covered day.
- **Two rows per purge, order-independent.** `reorgs` is a plain `MergeTree ORDER BY (chain, epoch)`, so a merge may reorder the armed and completed rows — nothing depends on it: `epoch_floor_v` takes `max(epoch)`, `current_epoch` takes `max(epoch)`, and every consumer of `completed` filters rather than picks a row (`store.rs:473`, `acceptance.rs:1113,1268,1297,1367,1807`).
- **Armed-but-uncompleted rows hide a window, and the crash matrix covers it.** `epoch_floor_v` counts armed rows (correct: under-count during the repair, never double count). `src/reorg/model.rs:397-415` implements the same interval rule and `check_clean` (`model.rs:2046-2120`) compares the resulting aggregate view against a clean index, so `a_rollback_interrupted_at_any_step_converges` / `a_gap_heal_interrupted_at_any_step_converges` (80 cases each, restart × discard × partial) really do assert that no window stays hidden.
- **The repair window cannot narrow between attempts on the EVM path.** `timestamp_span` reads min/max over **all** row versions (`store.rs:535-590`, no `FINAL`) and tombstones copy their row's timestamp (`schema.rs:133-167` builds positional column lists, avoiding the `SELECT * REPLACE` landmines); the purge takes the window twice and the wider one wins (`purge.rs:357-383`).
- **Side-table repair never crosses a chain or a family.** `Side::predicate` (`store.rs:124-137`) and `range_predicate` (`modules.rs:798-820`) always carry `chain = {chain}`, so a Solana purge touches only `chain = 1399811149` rows of the shared `launchpad_*` tables and an EVM purge only its own. `every_declared_side_table_is_covered_by_the_purge` (`store.rs:924-986`) derives the base→side map from the migration DDL and asserts the block column and the base filter exist. All `launchpad_*` side tables use `block_number`, so Solana's hard-coded column is right.
- **Month-split parts are complete in themselves on the EVM path.** Every core and module row type derives `Timestamped` from its block's `timestamp` (`modules.rs:383-401`); the two exceptions (`prediction_outcome_tokens`, `prediction_market_registries`) are `PARTITION BY chain` lookup tables, so the split does not apply. `store_window` (`db/mod.rs:826-898`) writes children → `blocks` → checkpoints per part with a per-part `FlushKey`, so a crash between parts leaves the later months as ordinary gaps.
- **Purge order and the checkpoint invariant.** `checkpoint_writes` (`store.rs:189-220`) emits the tombstone and the surviving remainders in one insert with distinct keys; a checkpoint may under-claim, never over-claim. `compaction_writes` (`ranges.rs:172-236`) merges only runs of ≥2 contiguous rows and never invents coverage. `Scope::Module` purges do not touch checkpoints (`store.rs:654`), so `indexer backfill` cannot race the compactor.
- **Clock going backwards.** `next_version` is monotone in-process and `Database::seed_version` (`db/mod.rs:533-585`) seeds it from `max(_version)` over every table the process writes plus `checkpoints`, warning when the stored version is ahead of the host clock; the Solana list correctly excludes `sol_token_balances` (a position would poison the clock) and `sol_dex_programs` (no `chain` column). A tombstone that still lost would fail loudly with `TombstonesNotConverging`, never silently.
- **Solana decode truth, what I checked directly.** Failed transactions are excluded outright (`svm/decode.rs:698-702`). Dispatch is on `(family, discriminator)` (`svm/launchpads.rs:989-1110`), so the two shared discriminators — `DISC_LAUNCHLAB_TRADE == DISC_PUMPFUN_TRADE_EVENT` (`programs.rs:720`) and `global:buy` shared by PumpSwap/pump.fun (`programs.rs:304`) — cannot cross-decode; the per-program layer dispatches on the *event*, not the instruction variant (`events.rs:11-18`). `owned_by` attributes a movement to its **nearest** registered venue ancestor (`decode.rs:440-457`), which is what splits a Jupiter multi-hop into one swap per venue instead of one merged swap. Routers are a separate list from `VENUES` (`programs.rs:266-290`) and only set `route_program`/`route_ordinal`; the Solana candles are keyed by `(pool_id, venue_program)` (`0042:66`), so a split route cannot merge. Liquidity add/remove (both mints the same way), flash loans (`mint_in == mint_out`) and self-transfers are all returned as `Liquidity`/`Unclassified` rather than swaps (`decode.rs:1279-1298`). When the pool side is genuinely ambiguous the decoder proposes both readings and **drops the trade** unless a venue event validates one (`decode.rs:777-833`) — it never guesses a direction. Token-2022 transfer fees are handled by reading the vault's real credit (`decode.rs:500-532`). `native_leg` refuses to use a lamport delta when two venue instructions resolve to the same authority (`decode.rs:476-494`), covering "the same pool touched twice".
- **Part 4 (SQL fixes, spot-checked).** All 21 guards are `AND length({<id>:String}) IN (40, 64)` in the filter that gates each view's output (8 in `0022_prediction_views.sql`, 13 in `0032_launchpad_views.sql`), and the id is left-padded correctly: `toFixedString(unhex(if(length({token:String}) = 40, concat('000000000000000000000000', {token:String}), {token:String})), 32)` (`0032:169-174`) — 12 zero bytes in front, matching §13. Empty/39/63-character parameters no longer select the 32-zero-byte bucket; >64 still throws `TOO_LARGE_STRING_SIZE`. The predictions padding fix replaces the old truncation with `toFixedString(concat(toFixedString('', 12), tk.address), 32)` at `0022:81,112,143,341,344,822,826,827`, so a Solana pubkey can no longer collide with an EVM token's decimals and rescale amounts by `10^decimals`. `dex_epoch_floor_v` is gone; all five DEX views now use the shared `epoch_floor_v`.
